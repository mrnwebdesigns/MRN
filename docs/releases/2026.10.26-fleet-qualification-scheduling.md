# Native qualification scheduling correction

The October 26 cumulative candidate passed independent package and native browser checks but failed full runtime QA with a 30-second PHP timeout, homepage smoke failure, 7.8-second TTFB and poor Core Web Vitals. It was not published. PHPStan completed with the existing 24 advisories.

The installed macOS `launchd.plist(5)` documentation says Standard is equivalent to omitting ProcessType, which still applies light CPU and I/O resource limits. The previous installer incorrectly described Standard as regular, unthrottled scheduling.

A sequential comparison used the identical candidate bootstrap, PHP binary, native database, browser assertions, execution limit and diagnostics. Both fresh fixtures activated all 34 default plugins without WooCommerce:

| Process type | Fixture startup | Measured request range | Browser/diagnostics |
| --- | ---: | ---: | --- |
| Standard | 116.634 seconds | 0.157–1.049 seconds | Pass |
| Interactive | 11.552 seconds | 0.174–0.363 seconds | Pass |

The Standard opcode cache retained about 18 MiB of free space after browser checks, with no full-cache condition or restart. The controlled comparison supports correcting the worker's resource policy; it does not by itself establish that every prior timeout had the same cause. Fresh complete release qualification remains required.

The installer now selects Interactive scheduling for this serialized, owner-requested source qualification workload. No request timeout, performance threshold, diagnostic check or publication gate is relaxed. No client-site or provider behavior changes.

For an existing installation, first confirm the worker is idle, preserve the owner-only LaunchAgent definition, unload that exact job, and rerun the accepted installer using the existing configuration and executable PATH. Preserve the old definition for rollback. Do not overwrite an unrelated definition or terminate another task's qualification.
