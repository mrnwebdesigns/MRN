# Explicit disabled content types and SEOPress

## Change and compatibility

MRN Admin Data Post Types and its loader advance from 0.2.1 to 0.3.0. The existing
Config Helper 0.1.74 Content Types extension owns the UI container; the MU plugin
owns the explicit `mrn_disabled_post_types` option and its behavior. No parent or
child theme edit is required. Existing `disabled_admin_cpts` entries keep their
menu-only meaning. Existing Content Only behavior is preserved. While a type is disabled, native
Config Helper saves retain its prior Hide, Content Only and search-destination
preferences even when those older controls are omitted from the form.

Installing this release does not disable Galleries or Case Studies on Trilliant
or any other site. Each site must explicitly adopt its intended selection.
Public URLs only change when that selection is made. Disabled public singles,
archives and exclusive taxonomy archives answer 404; no automatic redirect or
analytics, business-information, unrelated metadata or redirect-rule change is
introduced. Existing embedded/programmatic content and files remain available.
A normal WordPress Page using a similar slug is independent of the CPT archive
and needs its own content decision; the option never deletes that Page.

## Source acceptance and Fleet publication

Task acceptance requires regression checks, task-scoped MRN QA, PHP lint,
security/accessibility/performance review, diff check, and the staged commit
gate. A source commit/PR is reviewable implementation, not Fleet readiness.
After acceptance/merge, the existing serialized automatic publisher qualifies
clean cumulative merged source, reconciles the catalog and immutable lock,
builds every applicable distribution, publishes and verifies checksums. Preserve
the old distribution until all required checks pass. Never deploy alongside an
active Fleet update. This document is not a publication receipt.

Remote Config Helper parity and site-owner write-readiness are intentionally
outside local source acceptance: Config Helper bytes are unchanged and no remote
site is selected. Those checks belong to a later authorized rollout.

## Site adoption (separate authorization required)

1. Resolve the exact site URL, environment and live theme shape through the
   canonical MainWP/provider workflow. Refresh narrowly scoped inventory. Check
   the site knowledge, existing hold/operation state, source release checksums,
   backup-policy readiness and site-owner deployment access.
2. Inventory existing menu-hidden and Content Only selections, public singles,
   archives, exclusive taxonomy URLs, sitemap inclusions, terms and SEO values.
   Never infer intent from zero posts. Confirm the exact disabled selection.
3. Keep menu-only sites as they are. For Trilliant, explicitly review `gallery`
   and `case_study`; keep `team_member` enabled. Review indexed/backlinked URLs
   and choose useful redirects separately where needed before retiring routes.
   Save the complete previous `mrn_disabled_post_types` value for reversal.
4. Apply the published full Stack release through the normal backup-gated
   workflow. Before each remote config/database write create and verify a
   labeled database-only Updraft backup sent to its configured remote destination
   (or the site's explicitly approved native-provider backup exception).
5. Apply a reviewed, versioned, idempotent site configuration migration that
   merges only the approved slugs into `mrn_disabled_post_types`, preserving
   other explicit selections and all legacy Config Helper/content-only options.
   The native Config Helper control provides the equivalent guarded admin save.
6. Let the next complete WordPress request rebuild pending rewrites, then purge
   the relevant site/CDN/page/sitemap caches. Verify settings save/readback,
   missing-default warnings, XML/HTML choices and actual sitemap output,
   direct/paginated sitemap URLs, archives/singles and exclusive taxonomies.
   Verify Team Members, normal Posts/Pages, shared taxonomies and unrelated
   settings against the pre-change baseline. Rerun audit discovery as needed.
7. Report installed version/hash, selected state and public checks separately
   from source/Fleet status. No site is adopted by this source task.

## Rollback and re-enabling

Prefer restoring the complete previous disabled selection while retaining 0.3.0.
Re-enabling restores normal registration/discovery and the saved SEO/include
entries; previous menu hiding/Content Only preferences still apply. Let pending
rewrites rebuild, clear caches and repeat public/sitemap checks. Content,
attachments, terms, relationships, SEO options and historical audit rows are not
deleted by disable/re-enable.

If reverting code, restore the exact prior component and loader together through
the backup-gated Stack rollback workflow, then rebuild rewrite rules and clear
caches. Retain the explicit disabled option for recovery. Version 0.2.1 does not
honor it, so public routes can return immediately after a code rollback; review
that exposure before authorizing the rollback. Verify installed hashes and
public behavior. Restoring a redirect policy, if separately changed, requires
its own reviewed reversal.
