# Stack recovery candidate: October 5, 2026

Status: source and disposable recovery qualification; **not fleet-ready**.
No existing site is a deployment or test target for this cleanup.

## Change

Deployment Agent 0.2.6 closes a recovery gap in the existing authenticated
MainWP transport: a terminated request could previously leave moved components
without a complete durable rollback record. The agent now:

- Takes one nonblocking private writer lock across apply, rollback and incomplete-marker reconciliation.
- Copies and verifies every before-state before the first live rename, including empty directories.
- Atomically persists a schema-3 recovery journal and intent before each filesystem move.
- Recovers recorded rename gaps across both interrupted apply and interrupted rollback.
- Checks all snapshots and live paths before restoration, rejects unknown drift or aliases, and prevents an older rollout from overwriting a newer deployment.
- Retains completed rollback journals and snapshots, supports verified repeat rollback, and refuses reuse of a rollout ID.

The existing MainWP authenticated execution hook remains the only entry point.
No public REST/AJAX/admin-post endpoint, site content, editor interface, provider
credential, mail setting, or cache purge was added. The Dashboard's verified
remote database backup gate still applies to every real apply and rollback.

## Release and recovery limits

This candidate retains the exact `2026.10.05-stack-retirement-r1` baseline.
Its removed SEO/editor/SendGrid components remain available through their
previously verified Git bundles and restoration records.

The agent still swaps live directories individually. This is process-interruption
recovery for the current transport, not request-pinned, whole-cohort activation.
The separate immutable-component prototype is still excluded from default
installation. Do not send its ZIP to the ordinary WordPress plugin installer.

Legacy schema-2 rollback records retain their older guarantees and cannot be
used while newer journaled lineage exists. Private snapshots and transient
recovery workspaces are retained after rollback; cleanup is a separately scoped
operation after recovery acceptance. Disk capacity must accommodate snapshots,
staging and displacement copies. Files are flushed and synced where PHP
supports it, but directory fsync, power-loss durability and shared/remote
filesystem semantics are not qualified.
